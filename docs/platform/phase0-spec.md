## 3. 共通AIプラットフォームの設計案

### 3.1 中心となる考え方
4サービスはすべて「**現状を聞く → 計画を作る → 進捗を記録 → 計画を直す → 報告**」という同じ流れに乗る。違いは入力項目、生成ルール（プロンプト）、禁止表現、データ区分だけ。そこで次の共通部品を作り、サービスごとに設定ファイルで差を持たせる。

| 共通部品 | 役割 | サービス別の差（設定） |
|---|---|---|
| 入力フォーム | 現状と目標を聞く | 質問項目 |
| 計画生成 | ロードマップ・週次計画を作る | プロンプト、出力の型 |
| 安全チェック | 禁止表現・断定・保証表現を検出し止める | 禁止リスト（投資助言、合格保証、医療断定など） |
| 進捗記録 | 週次チェックイン | 指標（学習時間、貯蓄額など） |
| 再計画 | 実績との差から計画を直す | 修正ルール |
| 通知 | リマインド | 頻度 |
| レポート | PDF/HTMLで納品 | テンプレート |
| 計測 | 購入・利用・継続・返金 | 共通 |

### 3.2 段階的な構成（最初から作り込まない）

| 段階 | 構成 | 追加費用 | 承認 |
|---|---|---|---|
| **P1 手動納品MVP** | 販売は既存プラットフォーム（note/BOOTH等）、申込は無料フォーム、生成は Claude/ChatGPT の既存契約内で人が実行し確認、納品はPDF | 0円（販売手数料のみ） | 販売アカウント開設・販売開始はオーナー承認 |
| P2 半自動 | 生成プロンプトと安全チェックをこのリポジトリでコード化・テスト。納品物は人が確認してから送る | 0円（ローカル/CIのみ） | 実装は独立レビュー後 |
| P3 自動化 | 決済→生成→確認→納品→リマインドを自動化。有料API（従量課金）とサーバーレス無料枠を想定 | 月数百〜数千円【仮定】 | **有料API・ホスティング契約は事前承認** |

### 3.2.1 AI利用の線引き
- **P1（手動納品）**: 既存の Claude・ChatGPT 契約は、運営者が成果物を作る**補助**として使う。出力は運営者が確認・修正してから納品する。
- **アカウントを顧客と共有しない**（各社規約で認証情報の共有は禁止）。顧客に AI を直接操作させない。
- **P3（自動生成・大量処理）**: API 利用を前提に、1件あたりの費用を別途試算してオーナー承認を得てから始める。個人向けサブスクで顧客向け生成を自動実行しない。

### 3.3 データ区分と扱い

| 区分 | 例 | 保存 | 方針 |
|---|---|---|---|
| D0 公開 | LP、サンプル | リポジトリ | — |
| D1 連絡先 | 氏名・メール | 販売プラットフォーム内のみ | リポジトリに置かない |
| D2 一般 | 目標・進捗（③①） | P1ではフォームのみ。納品後90日で削除【仮定】 | 最小限 |
| D3 機微（家計） | 収入・支出・資産（②） | **他区分と分離**。口座番号・ID・パスワードは受け取らない | 金額は概算レンジで入力させる |
| D4 未成年 | 学年・成績（④） | **他区分と分離**。保護者が入力、本名・学校名は不要にする | 保護者同意を取る |

- AIサービスへ送る前に D1 を取り除く（匿名化）。送る項目は生成に必要な最小限に絞る。
- テスト・開発は架空データのみ。

### 3.3.1 保存・アクセス・削除（P1）
| 区分 | 保存場所 | アクセスできる人 | 保存期間【仮定】 | 削除手順 |
|---|---|---|---|---|
| D1 | 販売プラットフォーム | オーナーのみ | プラットフォームの規定 | プラットフォーム上で対応 |
| D2 | 申込フォームの回答（オーナーのアカウント） | オーナーのみ | 納品後90日 | 回答と生成用の作業ファイルを削除し、削除日を台帳に記録 |
| D3・D4 | D2とは別のフォーム・別フォルダ | オーナーのみ | 納品後30日 | 同上。顧客から削除依頼があれば7日以内に対応 |

- **公開リポジトリ（このリポジトリ）には顧客情報・秘密情報（APIキー、トークン、口座情報）を一切置かない。** 台帳も件数と日付のみで個人を特定できる情報を書かない。
- 申込フォームで「入力内容をAIサービスで処理すること」「保存期間」「削除依頼の方法」を明示し、同意を得る。④は保護者の同意とし、入力項目も必要最小限（学年・志望の種類・模試の偏差値帯・学習可能時間程度）にする。
- **顧客入力データと取引記録を分ける。** 削除期限の対象は顧客の入力内容と生成用の作業データ。決済・返金・会計の取引記録は、法令上必要な期間だけ必要最小限で別に管理し、削除依頼があっても法的な保存義務がある部分は例外とする（例外の範囲は販売開始前に確認）【要確認】。
- **AIサービスの確認**（販売開始前）: 送信先、利用目的、データの保存期間、学習に使われるかどうかの設定を確認し、学習利用はオフにする。

## 4. 4事業の同時開始プラン（v0.4）

v0.3 では③から順に出す案だったが、オーナー決定により4事業を同時に開始する。P1（手動納品）は追加費用がほぼ0円のため、同時開始でも金銭リスクはほとんど増えない。代わりに次の3つのリスクを上限と条件で抑える。

| リスク | 対策 |
|---|---|
| 納品の手間が4倍になる | 各サービス**先着3件**で受付を止める。納品作業の見積もりは合計9.9時間【仮定】だが、問い合わせ・申込確認・修正・返金・納品後の質問は含まないため、下の「作業時間の上限」で管理する |
| ②④は準備が多い（免責、同意、データ分離） | ②④は「免責表示・申込時の同意（④は保護者同意）・別フォーム／別フォルダでの保存」がそろうことを販売開始の条件にする |
| 集客が4つに分散し、1つあたりの訪問が減る | 判定は「訪問100未満なら需要を判断しない」のまま。Instagram は1アカウントに集中させ、投稿テーマで4事業を回す（4.1） |

### 作業時間の上限と納品範囲
- **P1期間（最初の12件）の作業時間上限は4事業合計20時間**（納品＋対応すべて）。超えそうな時点で全商品の新規受付を止め、見直す。
- 商品ごとに、1件の実作業が見積もりの1.5倍を2件続けて超えたら、その商品の受付を止める。
- 作業時間は1件ごとに「納品／問い合わせ・修正／返金対応」に分けて記録する。
- 各商品ページに**納品範囲・納期・修正回数（事実誤認と誤字の修正1回。方向性の変更は対象外）**を明記する。追加の相談は別商品とし、P1では販売しない。

### 4.1 Instagram の使い方【仮定】
- **役割は「知ってもらう」こと**。投稿本文にはリンクを置けないため、プロフィールのリンクから各サービスの販売ページへ案内する。
- **1アカウントで開始**（新規アカウントは4つに分けると各々が育たない）。共通コンセプトは「**AIで、仕事・お金・目標・学習の未来を設計する**」とし、4事業を投稿シリーズとして明確に分ける。
  | 曜日 | シリーズ | 誘導先 |
  |---|---|---|
  | 月 | 経営・仕事（①） | ①の販売ページ |
  | 火 | 家計・お金（②） | ②の販売ページ |
  | 木 | 目標達成（③） | ③の販売ページ |
  | 土 | 受験・学習（④） | ④の販売ページ |
- **シリーズ別に計測**：投稿ごとの閲覧数・プロフィールへのアクセス・リンクのタップ（Instagram のインサイト）、販売ページの訪問・購入（商品ごとに別のページ・別のリンクにして判別）。反応が偏れば将来のアカウント分割を判断する。
- **本人の顔出しなし**：図解カルーセル（例：家計の見直し手順、受験までの逆算表、目標のルート図）と短いリール。事例はすべて架空と明記する。
- **投稿の禁止事項**：収入・資産増加・合格の保証、個別銘柄の推奨、実在しない利用者の声。
- 新規アカウントは最初の数週間の露出が小さい見込み。補助として販売プラットフォーム内の検索流入（ココナラ等）を併用する。広告は使わず、使う場合は上限をオーナーが事前に決める。

- note は売上の振込1回につき270円がかかる（件数ではなく振込回数ごと）。
- 税金・返金・振込時期は売上台帳で別に管理する（個人情報は書かない）。個別に作り込む納品物（①③④）は申込情報のやり取りが必要なため、販売場所は規約確認のうえで決める（4章「販売経路の分け方と規約確認」）。

### 販売経路の分け方と規約確認
マーケットプレイスは外部決済・外部サービスへの誘導が規約で制限される場合があるため、経路ごとに商品を分ける。
| 経路 | 販売・決済 | 注意 |
|---|---|---|
| ココナラ等 | プラットフォーム内で完結 | 外部ページ・自社決済へ誘導しない |
| note | note 内で販売 | — |
| 自社ページ | 自社決済（導入はオーナー承認後） | 特定商取引法の表記が必要 |

**受入条件**: 各プラットフォームの最新の規約・手数料・禁止事項を販売開始前に確認し、確認日とともに記録する。

### 計測する指標
販売ページ訪問数、購入数、購入率、返金率、1件の作業時間、満足度、再購入・継続意向。経路別に記録する（`kpi.csv` 形式。個人情報なし）。

### MVP の判定基準（事前に固定）
判定は「需要」と「集客」を分けて行う。
- 「訪問」は**対象顧客のユニーク訪問数**（ページ表示回数ではない）。運営者自身・テストアクセスは除外する。
- 流入元ごとに購入率を集計する。
- 「有料5件」は成功の保証ではなく、P2 に進むための暫定的な合格ライン。購入数だけでなく購入率・満足度・作業時間を合わせて判断する。

| 状況 | 判断 |
|---|---|
| 30日で対象顧客の訪問が100未満 | **需要は判断しない。** 集客経路の検証を続ける（経路の追加・変更） |
| 訪問100以上で有料5件以上、作業30分以内/件、返金・苦情0〜1件、満足度平均4以上 | 継続し、P2（コード化）へ |
| 訪問100以上で有料1件以下 | 商品（説明・価格・内容）を変更して再検証。2回続けば撤退 |
| 作業60分超/件、または返金・苦情2件以上 | 販売を止めて内容を見直す |

広告費は使わない前提。使う場合は上限をオーナーが事前に決める。

### 4.3 ②資産シミュレーションの表示ルール
- 表示名は「**仮定条件にもとづく試算**」。予測・運用成果の保証ではないと明記する。
- 想定利回りは複数（例：0%・3%・5%）を並べ、**元本割れのケース**（マイナス利回り、途中の下落）も必ず示す。
- **インフレ**（物価上昇で実質的な価値が目減りすること）、**運用手数料**（信託報酬など）、**税金**の扱いを試算の前提として書く。
  - 課税口座：上場株式等・公募投資信託の譲渡益と配当等に原則 **20.315%**（所得税・復興特別所得税15.315%＋住民税5%）。税金は元本や評価額全体ではなく、課税対象となる利益にかかる。
  - NISA：非課税枠内の利益は非課税。一方、**損失は税務上ないものとされ、課税口座との損益通算・繰越控除はできない**。
- 個別の銘柄・投資信託・金融機関はすすめない。商品選びは利用者自身が行う旨を書く。
